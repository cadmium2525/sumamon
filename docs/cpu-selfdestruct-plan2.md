## 2. 原因 — 外向き入力を消しても、実際にはほとんど減速しない

MoB（waterfall_ruins・CPUレベル9）seed 11 のトレース。
`崖外` はマイナスが場内側、プラスが場外。

| フレーム | 崖外 | vx | 出来事 |
|---|---|---|---|
| f576 | -71 | +10.16 | 左の崖の71px内側。接地 |
| f577 | -82 | +10.16 | ジャンプ（残J 2→1） |
| f583–597 | -141→-278 | +9.8 | 空N。**右へ9.8px/フレームで飛び続ける** |
| f609–625 | -395→-354 | +9.45 | 通常必殺。中央を越えて右の崖へ |
| f616 | -439 | +9.45 | 空中ジャンプ（残J 1→0） |
| f874 | **+187** | +0.38 | **反対側の崖を越え、上必殺使用済・helpless → 落下** |

**CPUはステージを端から端まで空中を横断し、反対側から落ちている。**
吹っ飛ばされたのではなく、**自力で加速して**そうなっている。

### なぜ止まらないのか

`js/cpu-ai.js:256` の制動距離の見積もりが実態と合っていない。

```js
const brake = (vx * vx) / (2 * accel);   // accel = CONFIG.AIR_ACCEL = 0.18
```

この式は「逆方向を入力して `accel` で減速する」前提の距離。
ところが `:261-267` は**外向きの入力を消しているだけ**で、
逆方向を入れていない。入力が無い時の減速は
`CONFIG.AIR_FRICTION = 0.994` の掛け算（`js/fighter.js:566`）なので、
実際に進む距離はまったく違う。

| vx | 見積もり（accel 0.18で減速） | 実際（入力なし・0.994の摩擦） |
|---|---|---|
| 3.44（既定ステータス） | 33px | **570px** |
| 9.8（回避900） | 267px | **1624px** |

**約6倍の過小評価。** だから「まだ余裕がある」と判断したまま
反対側の崖まで運ばれる。既定ステータスでも570px出るので、
これは高ステータス専用の問題ではない（高ステータスほど致命的になるだけ）。

`:262` のコメントに「内側へ引き戻すのは復帰処理の仕事」とあるが、
`_recoveryIntent` は `_isInDanger` が真になるまで動かない。
足場より高い位置を横切っている間は `_isInDanger` が反応しないので、
誰も減速させないまま反対側へ抜ける。

## 3. 直すこと

### 修正1（本命）— 外向き入力を消すのではなく、内向きを入れて減速させる

`js/cpu-ai.js` の `_keepOnStage` 空中分岐（`:256` 以降）。
「入力を消す」を「逆を入れる」に変える。逆を入れて初めて `AIR_ACCEL` で
減速するので、`brake` の見積もりと実際の挙動が一致する。

```js
    const brake = (vx * vx) / (2 * accel);
    const outLeft = (stage.x - cx) + (vx < 0 ? brake : 0);
    const outRight = (cx - (stage.x + stage.w)) + (vx > 0 ? brake : 0);
    // 外向きの入力を消すだけでは止まらない。入力が無い時の減速は
    // AIR_FRICTION(0.994)の掛け算しかなく、実測で速度9.8なら1624px進む。
    // brake の式が前提にしている「accelで減速」を成立させるには、
    // 逆方向を入れて能動的に減速させる必要がある（同条件で267px）。
    if (outLeft > limit) {
      input.left = false; input.right = true; input.stickX = 1;
    } else if (outRight > limit) {
      input.right = false; input.left = true; input.stickX = -1;
    }
```

**注意点**
- `input.jump` はここで触らないこと（`:239` の既存判定に任せる）。
  復帰に必要なジャンプを潰す
- `_recoveryIntent`（`:513`）は `_keepOnStage` を通らない設計。
  この前提は崩さないこと。崩すと復帰の上必殺が消える
- 内向きを入れることで、追撃中に相手から目を離す形になる。
  それでよい。**自滅して相手にストックを渡すより弱い追撃の方がまし**、
  という判断は `PURSUIT_SAFETY = 0.1` の時点で既に確定している

### 修正2（本家準拠）— 空中で自力で出せる速度を下げる

`js/config.js:140` の `AIR_MAX_SPEED_RATIO: 0.86` を **0.5** にする。

これは「空中の最高速度をダッシュ速度の何割にするか」。
スマブラSPでは**空中最高速は走り速度のおおむね4〜6割**で、
自分の意思で横に出せる速さにはっきり上限がある。SPで空中横移動の主役は
加速ではなく**地上から持ち込んだ慣性**で、立ち止まって跳んで横を入れても
じわっとしか動かない。

現状の0.86では回避900のモンスターが
**自力で9.52px/フレーム**まで加速でき、上のトレースのように
空中でステージを横断できてしまう。CPUの判断をどれだけ賢くしても、
「自分から高速で場外へ出られる」物理が残る限り同種の事故は消えない。

**吹っ飛びの慣性は制限されない**ことを確認すること。
`js/fighter.js:568-572` は「すでに上限より速い方向へ入力しても
それ以上加速しない」という作りで、吹っ飛びで得た速度は
上限で切り落とさない。この性質は**壊さないこと**（1.50で
「のけぞりが切れた瞬間に吹っ飛びが急停止する」問題を直した箇所）。

**これはプレイヤーの操作感も変える変更**なので、更新履歴に明記する。
体感としては「空中で自分から横移動できる速さが遅くなる。
走ってから跳べば今までどおり速い」。

### 修正3 — 崖の外での追撃許可距離を、実際に戻れる距離に合わせ直す

`_pursuitLimit()`（`:183`）が返す 240/400/40 は**修正1・2の前に実測した値**。
修正1・2を入れると復帰性能が変わるので、**測り直して更新すること**。
測り方は「崖の外◯pxに、空中ジャンプ◯回残しで置き、
`_recoveryIntent` だけを回して戻れるか」。既存のコメント（`:162-177`）に
測定条件が書いてあるので同じ手順で。

## 4. 入れない案（検討済み・悪化を確認）

**`AIR_ACCEL` を回避ステータスでスケールさせる案は入れないこと。**
実装して測ったら悪化した（同一条件で自滅11回 vs 7回）。
制動が速くなる代わりに、外向きの加速も速くなるため。
今回の修正2は逆方向（最高速度を下げる）で、こちらが正しい。

## 5. 検証手順

### 5-1. 棒立ちの的だけで判断しないこと

前回の計測（プレイヤーを固定した的にする方式）は、今回の経路を
**まったく検出できなかった**（自滅0・崖越え0）。動かない的に対しては
CPUがそもそも追いに行かないため。**必ず両者が動く条件で測ること。**

### 5-2. 両者AIの対戦を作る

`InputManager.getPlayer1Input`（`js/input.js:18`）を差し替えて、
1PをもうひとつのCPUControllerで操作する。

```js
const origInput = InputManager.prototype.getPlayer1Input;
InputManager.prototype.getPlayer1Input = function () {
  const ai = window.__p1ai;
  if (!ai) return origInput.call(this);
  try { return ai.ctrl.decide(ai.bounds, [], Stage.platforms); }
  catch (e) { return origInput.call(this); }
};
```

対戦の開始は前回の計画書（`docs/cpu-selfdestruct-plan.md` §4-2）と同じ。
`AppFlow.showScreen('battle')` を呼ぶこと、`statOverrides` のキーは
`cpu1` ではなく `cpu`、`setBattleInputLocked(false)` が要ること、
`performance.now` を5倍速にすると実時間の1/5で済むこと、
`Fighter.prototype.update` のフックは一度だけ入れて外さないこと。
1P側にも `statOverrides.p1` で同じ高ステータスを入れる。

### 5-3. 指標と合格ライン

| 指標 | 定義 |
|---|---|
| CPU自滅 | `selfDestructs` の増加 |
| CPU撃墜され | `falls` の増加のうち自滅でないもの |
| CPU崖越え | 中心Xが足場の左右を初めて越えた回数 |
| 技発生 | `attackTimer` が0から正へ変わった回数（弱腰になっていないかの確認） |

四大大会3種＋レジェンド杯 × **8シード以上** × 各90秒、
1P側のレベルは7と9の両方で回す。

- **CPU自滅：レベル7で11→2以下、レベル9で8→2以下**
- **CPU崖越え：半分以下**（32→16以下、50→25以下）
- **技発生：修正前の9割以上**（弱腰になっていない確認）
- 既定ステータスの通常CPU戦（レベル1〜9）で自滅が増えていないこと
- 修行5コース（`js/practice.js`）が壊れていないこと。
  修正2は空中の最高速度を変えるので、跳び越え距離が変わる可能性がある。
  **マンディー砂漠・パパス雪山は過去に壊れた実績があるので必ず通しで見ること**

**修正前の数値も自分で取り直すこと。** この文書の数値をそのまま比較対象に
しないこと。`git worktree add` で修正前のコミットを別ディレクトリに出し、
別ポートで配信して同じスクリプトを両方に当てるのが手軽。
