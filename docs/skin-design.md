# マスモンのスキン（色変更）設計メモ

「虹彩の染色セット」でマスモンの色を自由に変えられるようにするための設計。
v1.05で実装し、実際に手で塗ってみて使いにくかったため v1.08 で方式ごと作り直した。

## 何を作るか

- モンスターの色をパーツごとに塗り替えられる。
- プリセット（本家スマブラのようなカラーバリエーション）＋自由色。
- 編集画面はズーム対応。細かい所も指定できる。

## 方式：素材（色のまとまり）の置換

領域（マスク画像）ではなく **色** で置き換える。こうすると専用モーションの
全コマへ作業ゼロで反映され、保存データも数百バイトで済む。

1. 立ち絵の色を **OKLab空間で k-means クラスタリング**し、14個前後の「素材」に分ける。
2. 素材ごとに新しい色を指定する。
3. 置き換えは素材の中心色を基準にした **相対値**。
   `新しい色 = 選んだ色 + (元の画素 − 素材の中心色) × 保持率`
   明暗の起伏（陰影とハイライト）は相対差として残るので立体感は保たれ、
   全体の色みは選んだ色そのものになる。

### v1（色相バケツ）をやめた理由 — 実測

v1は色相を20°刻みのバケツにまとめていた。イルミネで実測した結果：

| | 最大グループの占有率 | 部位に偏るグループ |
|---|---|---|
| v1（色相20°刻み） | **47.1%**（頭78%・胴91%・脚80%と全身に散在） | 0個 |
| v2（OKLab 14クラスタ） | **13.3%** | 14個中9個が特定部位に50%以上 |

明度と彩度を見ずに色相だけで分けていたため、同じ紫のマント・ドレス・ブーツが
1つのバケツに潰れ、どこをタップしても同じものが選ばれて塗り分けができなかった。

### 色だけでは分けきれない部分がある（測定済み・仕様上の限界）

5ビット量子化で色の分布を調べたところ、**画素の60%は複数の部位にまたがる色**を
使っていた。イラスト由来の絵は連続したパレットで塗られているため、
「マントだけ」「ドレスだけ」を色だけで完全に切り出すことは原理的にできない。

これを埋めるのが **「広さ」** の考え方。どこまで一緒に塗るかを利用者が決める。
- 広さ0% … タップした素材だけ
- 広さ25% … 同じ布の影やハイライトも巻き込む（実測でちょうど良い既定値）
- 広さ100% … 全ての素材

固定のしきい値でまとめる方式（色相でまとめる等）も試したが、イルミネのように
全身が同じ色相のキャラでは1つに戻ってしまい成立しなかった。

### なぜこの方式か

- **専用モーションにも自動で効く。** 色で置き換えるため、待機・ジャンプ・崖つかまり、
  そして Layer 1 で追加する専用モーションにも、コマごとの作業ゼロで反映される。
- **保存データが小さい。** 素材の中心色と新しい色の対応表だけ（数百バイト）。
  Firestore に載り、マルチ対戦の相手にも同期できる。
- ベースモンスターの定義（data/fighters.json）は一切変えない。マスモン側の属性になる。

### シェーダー／マスクを使っていない理由

- **シェーダー（WebGL）** … 塗り替えは1枚あたり8ms、素材の抽出も80msで、
  どちらもバトル開始前に1回だけ行う。実行中の負荷はゼロなので、
  WebGLを持ち込む複雑さに見合う利点が無い。将来コマ数が大きく増えたら再検討する。
- **マスク画像** … 部位ごとのマスクを持てば完全な塗り分けができるが、
  1体あたり30コマ以上あるため作成コストが現実的でない。
  透明部分（背景）はアルファ値に一切触れないことで保護している。

## 決まった仕様

### 塗り分けの粒度：素材 ＋ 「広さ」で調整

自動抽出だけだと、別パーツが同じ色の場合に一緒に変わってしまう。
逆に細かく分けすぎると、同じ布の影とハイライトが別々になって不自然になる。
どちらも固定値では決められないため、**利用者が「広さ」で調整**できるようにした。
離れた場所も同じ色にしたい時は「足して選ぶ」で選択に足していける。

v1にあった矩形での範囲指定は廃止した。マントとドレスのように矩形が重なる
パーツは分離できず、実際に使ってみて役に立たなかったため。

### 選択中の範囲を必ず見せる

v1では「何を選んでいるか」が画面に出ておらず、塗ってみるまで結果が分からなかった。
v2では選択中の素材を絵の上で黄色く光らせる（`Skin.selectionMask`）。

### 染色セットの消費：プリセットは無料・自由色は消費

- こちらで用意する固定カラーはいつでも無料で切り替えられる。
- オリジナルカラーを作る時だけ「虹彩の染色セット」を消費する。
- 確定前のプレビューは無料。

### 反映範囲：すべて

- バトル中のスプライト（全モーション）
- HUD・ストックアイコン
- ファイター選択・マスモン管理画面
- マルチ対戦の相手側にも同期

同じ塗り替え関数を通せば全部そろう。

## 実装の順序（案）

1. ~~**塗り替えエンジン**（新規 js/skin.js）~~ **済**（v1.08で作り直し）
   - OKLabでのk-means、相対値での置換、コマ画像の再描画とキャッシュ。
   - v1（色相バケツ・H/S置換）で保存されたデータも表示できるよう残してある。
   - 変換表はピクセル色をキーにしたキャッシュで持つ。バトル開始前に1回だけ実行。
     実測でイルミネ1枚あたり 素材抽出80ms・塗り替え8ms。実行中の負荷はゼロ。
2. ~~**保存とデータ**~~ **済**
   - `masmon.skin = { version:2, materials:[{ lab, color }] }` を MasmonStore へ。
   - マルチのロースター送信にも載せる（js/multiplayer.js）。
3. ~~**表示側の差し替え**~~ **済**（v1.04）
   - `Fighter._skinned(image)` を1か所通すだけで、立ち絵・状態モーション・技モーション・
     歩行シートの全てが塗り替わる。1枚につき1回だけ塗り、Fighterごとに覚えておく。
   - パーツ分割・武器レイヤーも `_skinned()` を通した絵から切り出している。
   - HTML側（`<img>`・背景画像）は `Skin.paintInto(要素, src, skin)`。
     データURLへの変換は非同期なので、先に元の絵を入れてから差し替える。
     変換済みなら待たずに入れるので、コマ送りでも点滅しない。
   - HUD・リザルトは Fighter の `skinnedIconSrc` / `skinnedSpriteSrc` を使う。
     セーブに載る `stockIconSrc` は元のパスのまま（データURLだと保存が膨らむため）。
4. ~~**編集画面**（マスモン管理から開く）~~ **済**（v1.05／v1.08で作り直し）
   - ズーム（ピンチ・ホイール・ボタン）とパン付きのキャンバス。
     動かさずに離した時だけ「タップ」として素材を拾う。
   - 選択中の素材を絵の上で光らせる。塗る前に必ず結果の範囲が見える。
   - 「広さ」で、同じ布の影やハイライトをどこまで巻き込むかを調整できる（既定25%）。
   - 「足して選ぶ」で、離れた場所の素材も同じ選択に足せる。
   - 消費：`Skin.cacheKey(draft)` がプリセットか空と一致すれば無料、
     それ以外は `dye_kit` を1個消費する。確定前のプレビューは常に無料。
5. ~~**プリセット**~~ **済**（v1.05／v1.08で作り直し）
   - モンスターの色から作る。各素材の色みだけを目標の色相へ寄せ、
     明るさと鮮やかさは元のまま残すので陰影の構造が崩れない。
   - 一番多い素材との色相差を0.4倍に縮めて残すので、
     2色構成のキャラは2色構成のまま色だけ変わる。
   - 無彩色（白・黒・灰）は塗らない。目や輪郭まで染まるのを防ぐため。
   - この作り方なら、スタジオで後から追加したモンスターにも自動で用意される。

## 注意点

- パーツ分割（v1.01）と武器レイヤー（v1.00）は、**塗り替えたあとの絵**から切り出すこと。
  順序を逆にすると元の色のまま切り出されてしまう。
- 自動モーション（v0.98）は変形だけなので影響を受けない。
- 塗り替えた結果もキャッシュしないと、画面を移動するたびに再計算になる。
  （fighterKey + スキンの内容）をキーにしたキャッシュを持つ。
- 素材の中心色(lab)は `extractMaterials` の時点で保存精度(小数4桁)に丸めること。
  あとから丸めると、編集画面で作った値と保存された値がわずかにずれ、
  「プリセットと同じ内容なのに有料と判定される」といった食い違いが出る。
- 保存済みスキンの復元は添字ではなく中心色の近さで割り当てること。
  将来こちらで素材の数を変えても、既存マスモンの色が入れ替わらない。
